# Production Restructure & Python Toolchain Bootstrap

**Date:** 2026-05-10
**Status:** Approved (design phase) — pending user review of this written spec
**Scope:** Whole monorepo polish, Python-side focus

## 1. Purpose

The repo currently has empty stub directories under `apps/api/app/`, an empty `apps/mcp/`, empty `packages/{shared-types,ui}/`, and a placeholder `app/main.py` exposing only `/health`. There is no Python virtual environment provisioned for the chosen toolchain (`uv`), and no project-level Python packaging (`pyproject.toml` and `Dockerfile` exist for `apps/api` only because they were just added by the user as authoritative artifacts).

This spec defines the file/architecture restructure to bring the repo to a production-grade starting shape and the steps to provision a `uv`-managed virtual environment for `apps/api` driven by the existing authoritative `apps/api/pyproject.toml`.

It does **not** introduce business logic for any feature in the P1 slice plan. Every authentication, task, calendar, mood, scheduling, MCP tool, and adapter implementation remains out of scope and is deferred to its own slice.

## 2. Authoritative artifacts (do not regenerate)

The following files are the source of truth and must not be regenerated, replaced, or rewritten under any circumstance during this work:

- `apps/api/pyproject.toml`
- `apps/api/Dockerfile`

When a new dependency is needed, edit `apps/api/pyproject.toml` in place and run `uv sync` to regenerate `apps/api/uv.lock`. The Dockerfile pattern (uv-based two-stage build, `/opt/venv` install target, non-root `lockin` user, `libpq5` runtime, httpx-based health check) is the template from which `apps/mcp/Dockerfile` is derived.

## 4. apps/api architecture — layered with explicit ports-and-adapters in `adapters/`

Layering convention (the only allowed import direction is downward; nothing in `db/`/`models/`/`adapters/` may import from `api/` or `services/`):

```
api/v1/routes  ─────┐
                    ├─►  services  ─►  models, db, adapters (via Protocols)
api/v1/deps   ─────┘
                       services  ─►  events.publisher
```

- `api/v1/routes/*.py` — only HTTP concerns: parse Pydantic request, call service, return Pydantic response. No business logic.
- `api/v1/deps.py` — FastAPI `Depends()` providers: db session, current user resolution, idempotency-key extraction. Wires concrete adapters into services on each request.
- `core/config.py` — `pydantic_settings.BaseSettings` reading env. Single global `settings = Settings()` instance.
- `core/security.py`, `core/logging.py`, `core/errors.py`, `core/idempotency.py` — cross-cutting infrastructure. No domain knowledge.
- `db/base.py`, `db/session.py` — `DeclarativeBase`, `create_async_engine`, `async_sessionmaker`. Models inherit from `Base` defined here.
- `models/` — SQLAlchemy ORM, one file per aggregate root (e.g., `task.py`, `user.py`).
- `schemas/` — Pydantic v2 DTOs grouped by aggregate; `TaskCreate`, `TaskRead`, `TaskUpdate` co-located.
- `services/` — pure business logic, takes a session + Protocol-typed adapters, returns domain models or schemas. Transport-agnostic; reusable by HTTP routes, Temporal workflows, and CLIs.
- `adapters/` — the **only** place ports-and-adapters lives.
  - `ports.py` defines `typing.Protocol` interfaces (`LLMPort`, `CalendarPort`, `VoiceTranscriberPort`). No `abc.ABC`, no inheritance.
  - Concrete implementations are plain classes that structurally satisfy a Protocol. They live in subpackages by category (`llm/`, `calendar/`, `voice/`).
  - Tests construct trivial fakes that also structurally satisfy the Protocol; no mocking framework needed for adapter swaps.
- `events/publisher.py` — thin `XADD` wrapper accepting an event Pydantic model from `events/schemas.py`. Always called by services after a successful DB commit (dual write is acceptable for slice 0; outbox pattern lands in slice 2).
- `events/schemas.py` — Pydantic mirror of `packages/events/schema.ts`. Hand-maintained for now; codegen is a separate future task.
- `workers/temporal/client.py` — Temporal client factory. `workflows/` holds workflow definitions added per slice.

`workers/temporal/client.py` must target **Temporal Cloud** in all non-local environments (staging, production). The client factory reads `TEMPORAL_HOST`, `TEMPORAL_NAMESPACE`, and `TEMPORAL_TLS_CERT`/`TEMPORAL_TLS_KEY` from env (via `app.core.config.settings`). Local dev defaults to `localhost:7233` with no TLS. Self-hosting Temporal is explicitly deferred to P2 at the earliest per the Technical Roadmap; provisioning a Temporal Cloud namespace is a Week 1 DevOps task, not a Week 9 one.

## 5. Python toolchain & venv provisioning

- Interpreter: Python 3.12 (pinned by `apps/api/.python-version` and `pyproject.toml`'s `requires-python = ">=3.12"`).
- Tool: `uv` ≥ 0.11. Already installed via `python -m pip install --user uv`. Satisfies the `[tool.uv] required-version = ">=0.5.0"` constraint in pyproject.
- Venv location: `apps/api/.venv` (per-service, matches the existing convention from `bootstrap.ps1`).
- Provisioning steps:
  1. Remove existing `apps/api/.venv` (created by plain `python -m venv` + pip during the original bootstrap).
  2. From `apps/api/`, run `uv venv` — creates `.venv/` using Python 3.12.
  3. Run `uv sync --extra dev` — resolves dependencies from authoritative `pyproject.toml`, generates `uv.lock`, installs runtime + dev deps, and editable-installs the `app` package (because `[tool.uv] package = true` + hatchling build target).
  4. Smoke-verify imports for the major runtime libs (`fastapi`, `sqlalchemy`, `alembic`, `redis`, `temporalio`, `structlog`, `opentelemetry`).
  5. Boot `uvicorn app.main:app` on port 8000 and verify `GET /health` returns `{"status":"ok"}`.

For `apps/mcp` the same recipe applies once its derived `pyproject.toml` lands: `uv venv` → `uv sync --extra dev`.

## 6. apps/mcp — derived from the apps/api pattern

- `pyproject.toml`: same structure, trimmed dependencies (no fastapi, sqlalchemy, asyncpg, psycopg, alembic, temporalio, passlib, jose, authlib). Includes `mcp` SDK, `httpx`, `pydantic`, `pydantic-settings`, `structlog`, `opentelemetry-*`. Dev extra mirrors `apps/api`.
- `Dockerfile`: copy of the `apps/api/Dockerfile` two-stage pattern with these deltas:
  - Build context paths swapped to `apps/mcp/`.
  - No `alembic` directory or `alembic.ini` copied.
  - Drop `libpq5` from runtime apt install.
  - `CMD` runs the MCP entrypoint. **Stdio transport** is the target for local development and automated validation tests (Weeks 9–10). **HTTP/SSE transport** (required for production deployment and for Claude, ChatGPT, and Gemini to reach the server over the network) must land in the same slice — it is not deferred. The P1 exit criteria requires MCP to be verified against all three platforms in a deployed environment, which stdio cannot satisfy. `apps/mcp/app/transport/` should contain both `stdio.py` and `sse.py`; the entrypoint selects via a `MCP_TRANSPORT` env var.
- Same ruff/mypy/pytest config blocks, same `[tool.uv]` block.

## 7. Quality tooling

All tool config for Python services lives inside each service's `pyproject.toml` (already provided for `apps/api`; mirrored into `apps/mcp/pyproject.toml`). Repo root holds only the orchestration:

- `.pre-commit-config.yaml` runs:
  - `ruff` (lint + format) on staged Python
  - `mypy` on staged Python
  - `detect-secrets` baseline scan
  - `check-yaml`, `end-of-file-fixer`, `trailing-whitespace`
  - `pnpm lint` for staged TS files (best-effort)
- `.editorconfig` — 2-space indent for TS/JSON/YAML, 4-space for Python, LF line endings, UTF-8.
- `.gitignore` extended with: `.venv/`, `.uv-cache/`, `.ruff_cache/`, `.mypy_cache/`, `.pytest_cache/`, `__pycache__/`, `*.pyc`, `htmlcov/`, `.coverage`.
- `Makefile` exposes:
  - `make api` → `cd apps/api && uv run uvicorn app.main:app --reload`
  - `make api-test` → `cd apps/api && uv run pytest`
  - `make api-lint` → `cd apps/api && uv run ruff check . && uv run mypy app`
  - `make api-fmt` → `cd apps/api && uv run ruff format .`
  - `make mcp`, `make mcp-test`, `make mcp-lint`, `make mcp-fmt` — analogous
  - `make up` → `docker compose -f infra/docker/docker-compose.yml up -d`

Pytest coverage threshold is left at whatever `apps/api/pyproject.toml` defines (currently no `--cov-fail-under`); this spec does not modify the authoritative pyproject.

## 11. Risks & mitigations

- **uv version drift between dev and Docker.** Dockerfile pins `ghcr.io/astral-sh/uv:0.5`; local has 0.11. `uv.lock` is forward-compatible across uv versions, so this is fine. If lockfile format ever changes, the Dockerfile pin can be bumped in a follow-up.
- **psycopg[binary] on Windows.** Wheels exist for 3.12; `uv sync` should resolve without compiling. If it fails, fall back to `psycopg[c]` is **not** an option per pyproject; we'd need to install Postgres client libs locally. Document only if encountered.
- **Editable install of `app`.** `[tool.uv] package = true` plus the hatchling target installs `app` as an editable package. This means `from app.foo import bar` works from any cwd inside the venv. Tests must use the same import style; `conftest.py` does **not** need `sys.path` manipulation.
- **Stale `apps/api/.venv` deletion.** Recreating the venv is destructive. Confirmed acceptable: the venv was created by `bootstrap.ps1` with pip-installed pinned packages and contains no user code.
